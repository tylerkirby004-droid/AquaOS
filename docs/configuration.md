# Configuration v1

AquaOS reads one explicit YAML file, overlays only documented deployment
environment variables, validates the complete result, and activates an
immutable copy. `configs/schema-v1.json` documents the public shape; Go
validation remains authoritative for cross-references, units, ranges, and
safety invariants.

Every file must declare `schema_version: 1`. Unknown fields and unsupported
versions are rejected. There is no implicit forward migration yet; a future
schema version must include an explicit migration and rollback path.

## Safe defaults

Omitted optional values receive broker-independent defaults: MQTT disabled,
the hardware-incapable simulator enabled, HTTP bound to `localhost`, bounded
timeouts, and no inventory. Defaults cannot activate physical equipment.

## Overrides and secrets

The supported overrides are `AQUAOS_LOG_LEVEL`, `AQUAOS_HTTP_ADDRESS`,
`AQUAOS_MQTT_ENABLED`, `AQUAOS_MQTT_BROKER`, `AQUAOS_MQTT_CLIENT_ID`,
`AQUAOS_MQTT_SITE_ID`, `AQUAOS_MQTT_USERNAME`, `AQUAOS_MQTT_PASSWORD`,
`AQUAOS_MQTT_REQUIRED_FOR_READY`, and `AQUAOS_SIMULATOR_ENABLED`.

`mqtt.password` is forbidden in YAML and must come from
`AQUAOS_MQTT_PASSWORD` or the service manager's secret facility. Redacted
diagnostics replace it with `[REDACTED]`. The active SHA-256 digest is computed
from redacted canonical JSON, so it identifies operational configuration
without becoming a verifier for secret guesses.

MQTT payload, offline queue, idempotency window, and reconnect backoff limits
are explicit YAML fields. They have conservative bounded defaults and are
validated whenever MQTT is enabled. Topic names and delivery policies are not
free-form configuration; they are generated by the versioned registry so a
deployment cannot accidentally retain commands or publish wildcard topics.

## Validation

Errors begin with a stable path such as `inventory.sensors[0].unit` and carry a
stable internal code. IDs use lowercase letters, digits, and hyphens. Device
references must resolve, configured units must be canonical, ranges must be
finite and ordered, and IDs must be unique within their registry.

The inventory section validates deploy-time identity references. Runtime
registration uses the Prompt 3 typed domain and ownership contracts; automatic
activation of configuration inventory remains an orchestration concern.

## Reload policy

Reload is serialized and planned against the active immutable snapshot. The
only hot-reloadable field in v1 is `application.log_level`; it is applied to the
live structured logger. Listener, lifecycle, MQTT, adapter, inventory, and
schema changes are rejected with restart reasons. Loading, validation,
planning, audit publication, or activation failure preserves the old snapshot
and digest.

## Lifecycle and health

Startup follows dependency order; shutdown and rollback use reverse order.
Aggregate and per-component timeouts are external configuration. Components
own their goroutines, derive them from the supplied context, and join them in
`Stop`.

Health reports process liveness separately from readiness. Required component
failure is `unhealthy` and blocks readiness. Optional integration failure is
`degraded` but cannot stop authoritative local control.
